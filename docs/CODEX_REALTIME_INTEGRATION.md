## 统一配置和订阅授权

- “服务连接”支持 API 模型引用与 ChatGPT 实时语音。API 复用原模型配置及密钥，不复制凭据到新表；可信模型配置接口已验证设备选择会覆盖本次 LLM 引用，恢复默认后回到原模型，智能体本身的模型配置不被改写。未向真实 API 供应商发起调用。
- ChatGPT 连接固定使用已注册的 local 节点及 `gpt-6.1-terra` 执行模型。用户先保存，再点击订阅授权；运行节点通过 Codex 的 `chatgptDeviceCode` 生成一次性授权码，用户在 OpenAI 官方页面完成确认。该流程依据 [Codex app-server 官方文档](https://learn.chatgpt.com/docs/app-server)。这里的订阅授权与控制台账号登录是不同事项。
- 本次用户已在官方页面完成授权；Java 管理 API 和真实页面均显示已授权。重启授权运行节点后仍能读出授权状态，说明凭据已持久化，而非仅存在浏览器内存。
- 界面“已授权”和“语音连通性待确认”分别表示账号状态与运行健康状态；不会仅凭保存或登录就声称语音链路可用。下文的合成音频测试单独记录了实际语音验证，尚未做常驻健康探测并回写 UI 状态。

## 与日常 Codex 登录隔离

每个控制台用户和连接使用专门的 `CODEX_HOME`：`account_profiles_dir / ownerId / connectionId`。运行节点强制 `cli_auth_credentials_store="file"`，不读取、复制或退出日常 Codex 账号，不使用系统 Keychain 存放这条连接的授权。

路径只接受数字用户 ID 和规范 UUID；拒绝符号链接、异常凭据硬链接、日常 Codex 目录，以及代理工作目录内部或其上级。目录权限 0700，凭据文件 0600。临时授权码不写入数据库、日志或浏览器存储，关闭弹窗会清除前端副本。

已实际核对：

1. 授权前，新目录显示未登录，没有复用日常账号。
2. 用户确认后，独立 `auth.json` 存在，权限符合要求。
3. 原日常 `auth.json` 的 SHA256 在授权前后和原生语音测试后完全相同；报告不包含原文件内容和指纹值。
4. 本机原有 `codex login status` 仍返回 `Logged in using ChatGPT`。
5. 授权运行节点重启后，独立账号依然可读。

这验证了本次本机隔离行为，不是对上游未来版本或任意系统凭据后端的保证。

## 访问控制和生命周期

- 所有控制台管理和账号代理接口使用原有 Shiro 认证，要求超级管理员，并再次校验连接与设备归属。其他管理员不能替该用户授权，普通用户不能访问管理接口。
- Java 只代理主机配置中的固定运行节点，浏览器无法提供 URL、文件路径或原始 Codex RPC。非回环 HTTP 节点被拒绝；远端必须 HTTPS。
- Python 内部授权接口需要服务端共享密钥，还须主机明确许可该控制台用户。允许的操作仅 status/start/cancel；请求大小最多 4096 字节，支持对分块请求限流。无订阅或 API token 返回浏览器；授权响应带 `Cache-Control: no-store`。
- 用户许可名单、工作目录与运行开关由主机配置控制，管理 API 参数不能覆盖。用户 ID 兼容 Java Long 字符串序列化。
- 同一连接重复点击复用已有授权请求；最多四个待确认登录，启动和状态进程也有限并发。请求十分钟超时后取消并回收；取消、失败、进程退出及服务停止均有清理。若用户刚完成官方确认时取消等待，返回真实的已登录状态，不误报未授权，也不退出已完成的独立账号。
- 修改连接通过修订号和数据库条件更新防止并发覆盖。设备重新绑定其他用户时，旧连接不能继续被新所有者解析。设备选择和停用在下一次连接生效；即时断开或撤销现有语音连接尚未实现。

## 设备语音接入

实际分支在 `core/websocket_server.py` 原有连接处理器之前进入 opt-in realtime 路由。控制台选择模式会先验证设备 HMAC 令牌，再从真实管理 API 查找所选连接和所有者许可；查找失败不回退到其他模型或日常订阅。选中的订阅连接必须有专用授权文件。每台设备最多一个活动连接。

设备协议支持 WebSocket v1/v2/v3、单声道 16 kHz Opus。hello 在认证和协议检查后尽快响应，Codex 后台启动与有限接收缓冲并行；启动缓冲最多十秒音频、256 KiB 和十六条控制，恢复后按原速投递，超限以 1013 关闭。设备断开会取消启动，后端异常会关闭连接并释放自有进程。

媒体通过真实 Codex WebRTC，不把转写文字当成音频开关；输出使用服务端 PCM 活动判断播放起止。明确 abort 清理旧输出。aiortc 1.15.0 内部连接任务通过版本特定适配串行管理，在关闭前取消并等待，失败标记纳入验证。以上组件此前的真人语音结果不在本轮重复采集。

服务端示例仅作部署说明，未应用到实体设备：

```yaml
codex_realtime:
  enabled: false
  console_selection: true
  allowed_user_ids: []
  workspace: /absolute/path/to/agent-workspace
  account_profiles_dir: /absolute/path/to/private-codex-profiles
  account_control:
    enabled: false
```

管理后端需配置固定 `service-connections.runtime-url`，以及与运行节点匹配的服务端密钥。不要把私有配置、密码、session token 或 `auth.json` 作为报告附件或提交到 Git。

## 实体 ESP32 的只读核查

2026-10-29 再次检测到 `/dev/cu.usbmodem1101`，USB 产品名 `USB JTAG_serial debug unit`，VID/PID 为 `0x303a / 0x1001`。官方控制台的某测试智能体显示在线，设备备注 wha103，固件 2.0.5，协议“开源版”。尚未证明 USB 设备与该条目是同一块硬件；也不能根据 USB 标识确定具体芯片、Flash 或 PSRAM 容量。

上游 [自定义服务器设置文档](https://github.com/xinnan-tech/xiaozhi-esp32-server/blob/1a095d5bed23e49a17f817c7f378e2a86f298dfc/docs/firmware-setting.md) 提供在配网高级选项设置 OTA 地址的方法；[v2.0.5 ota.cc](https://github.com/78/xiaozhi-esp32/blob/v2.0.5/main/ota.cc) 优先读取 NVS 的 `wifi.ota_url`，为空时才用编译默认值。因此已有固件可能无需重刷，但不能仅凭版本号断言厂商 WHA103 构建具有同样入口。

没有打开串口、重置设备、读取固件或密钥、修改地址、切换官方控制台设置或刷固件。进入配网模式或保存 OTA 地址会影响设备当前连接，尚未执行。官方条目原有 OTA 升级开关也保持不变。
